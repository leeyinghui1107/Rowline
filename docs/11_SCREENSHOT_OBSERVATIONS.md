# 11 · 原版实机截图观察（黑盒证据）

> 证据来源：原版 WinLinez v1.30 在 Windows 上的实机运行截图（用户提供）。
> 本文件记录**从截图直接读到的事实**，并标注它证实/修正了哪些静态分析结论。
> 与 `docs/03_FEATURE_SPEC.md` 的关系：截图是**行为层面**的最高优先级证据，
> 静态分析结论与之冲突时以截图为准。

## 2. HUD 栏布局（自左向右）

```
┌──────────┐   ┌────┐  ┌───┬───┬───┐   ┌────┐   ┌──────────┐
│  100     │   │下组 │  │ ● │ ● │ ● │   │颜色│   │   160    │
└──────────┘   └────┘  └───┴───┴───┘   └────┘   └──────────┘
   分数框        标签     预览球组      标签        分数框
```

| 元素 | 观察 | 含义 |
|---|---|---|
| 左分数框 | `100` | 某个分数（**当前分或最高分，待定**） |
| `下组` | 标签 | **"下一组"** |
| 三个预览格 | 截图 1：红/品红/黄；截图 2：黄/红/暗红 | **下一组 = 3 颗球** ⭐ |
| `颜色` | 标签 | **"颜色/形状"** 模式指示（对应菜单项 `使用形状`） |
| 右分数框 | `160` | 另一个分数 |

### 2.1 ⭐ 最重要的新事实：**下一组是 3 颗球**

这直接修正了 `docs/03` §8 里"补球数量 ⬜ 未定"的假设：

* 游戏**预先预告接下来的 3 颗球**；
* 因此"补球"的自然实现是：维护一个长度为 3 的**待用球队列**，队首的球被消耗时从队尾补入新的随机球；
* 这解释了**截图中稀疏的棋盘**——棋盘并非初始满盘。
  （新局的球数后来由截图 1 直接确定为 **5 颗**，见 §5c。）

> 静态分析只能看到 `GetPrivateProfileIntA` 读 `ShowNext`（"显示下一组"），
> **看不到"下一组 = 3 颗"**。这是截图独有的信息。

### 2.2 两个分数框

截图 1（游戏结束）与截图 2 都显示 `100` / `160`。静态分析确认存在两个独立的量：

| 量 | 地址 | 含义 |
|---|---|---|
| 当前局分数 | `0x40B06C` | 本局得分 |
| 最高分 | `0x40B2A8` | 榜单第 1 条的分数（默认 100） |

**假设**：左框 = 当前分（100），右框 = 最高分（160）？还是相反？
静态分析里 `0x40B2A8`（最高分）的**默认值正是 100**（ wiped 榜单的记录 0 = 100 分），
因此 **右框 `160` 更可能是当前分，左框 `100` 是最高分**（即默认榜单的 100）。
⚠️ 仍需 `BB-N02`（HUD 数值表）以 100% 确认。

## 5. 游戏结束对话框

| 观察 | 结论 |
|---|---|
| 标题 `WinLinez v1.30` | 与 `VERSION/1` 一致 |
| 一个**黄色警告三角**图标 | `MB_ICONWARNING` |
| 文字 `游戏结束!` | 简体中文 |
| 一个 `确定` 按钮 | **只有 OK**，不是 Yes/No |

> 静态分析找到的 `MessageBoxA` 标志 `0x34` = `MB_YESNO|MB_ICONWARNING`，
> 那是**反作弊**提示（带是/否）。
> **本对话框是另一处** `MessageBoxA`，标志应为 `MB_ICONWARNING`（仅 OK）。
> 这解释了为什么会出现"两个不同标志的 MessageBoxA"。

## 5b. ⭐ 榜单格式已确定；这是**单人**游戏，不是人机对战

第三张截图（总榜对话框）给出了此前完全未知的事实：

```
总榜
┌────────────────────────────────┐
│  1. 挑战者                 160 │
│  2. 国王                   100 │
│  3. - 空的 -                 0 │
│  4. - 空的 -                 0 │
│  ...                           │
│  16. - 空的 -                0 │
└────────────────────────────────┘
   [清除]              [确定(O)]
```

| 事实 | 含义 |
|---|---|
| 榜单**恰好 16 行** | 与静态分析的 `TABLE_LEN = 16 × 32 B` 完全吻合 ⭐ |
| 空槽的占位文字是 **`- 空的 -`**，分数 `0` | 榜单的渲染格式已确定 |
| 行的格式是 **`N. 名字    分数`** | 同上 |
| 第 1 名 `挑战者` 160 分，第 2 名 `国王` 100 分 | 两者都是**历史记录**；`国王` 是出厂默认记录 |
| 对话框有两个按钮：**清除**（带禁止图标）与 **确定(O)**（带勾图标） | 榜单可清空 |

**修正：不存在 CPU 对手。** 早先根据「国王 / 挑战者」两个名字推断的
「人机对战」是错的。二进制与实机观察给出的是：

* `0x40B2A8`（左框，`国王`）是**历史最高分 / 记录分**，只在读榜和游戏结束时更新；
* `0x40B06C`（右框，`挑战者`）是**本局当前分**，落子消线时增加；
* 空闲 480 秒的连续截图完全不变，进程没有任何自动落子；
* `0x402CB1` 的插入逻辑只在**游戏结束**（`0x4032E2`）时调用一次。

因此 HUD 的语义是：

| 截图 | 左框 | 右框 | 解读 |
|---|---|---|---|
| 第 1 张（**新局**） | **160** | **0** | 左 = 历史记录 160，右 = 本局 0 |
| 第 2/3 张 | **100** | **160** | 左 = 记录 100，右 = 本局 160 |
| 榜单 | — | 挑战者 160 / 国王 100 | 与 HUD 完全一致 ✅ |

**名称输入对话框**（第 2 张截图）

| 元素 | 内容 |
|---|---|
| 提示 | `输入你的名字:` |
| 输入框 | 预填 **`挑战者`** |
| 按钮 | `确定(O)`（带勾图标） |

→ 玩家的默认名就是 `挑战者`。该框只在**游戏结束且分数进入榜单**时弹出
（`0x402CB1` → `DialogBox(1002)`），不是每次消线都弹。输入并确定后写入
分数、随后立刻显示总榜（`DialogBox(1001)`）。

## 5d. ⭐ 布局：公式已由反汇编与实机双重确认

第 1 张是**窗口模式（桌面 200% 缩放）**，第 2 张是**同一局的全屏**。
两张图状态完全相同（5 颗球位置、3 颗预览球、160/0 分数都一致），
因此可以**交叉验证布局**。

`WM_SIZE` 的处理在二进制里出现两次（`0x402EA7` 与 `0x4036E8`），
算术完全一致，因此常量没有歧义：

| 全局 | 公式 | 含义 |
|---|---|---|
| `0x40B060` | `(clientW - 0x148) / 2` | 棋盘 x |
| `0x40B064` | `(clientH - 0x178) / 2 + 0x2E` | 棋盘 y |
| `0x40B070` | `clientW - 0x60` | 棋盘区宽度 |
| `0x40B078` | `(clientW - 0x6C) / 2` | **预览球组**的 x（不是棋盘！） |
| `0x40B088` | `((clientW - 0x148) / 2 - 0x3A) / 2` | 左角色 x |
| `0x40B08C` | `(clientH - 0xEA) / 2 + 0xEA` | 角色底座 y |
| `0x40B098` | `t + 0x148 + ((t - 0x3A) / 2)`，`t = (clientW - 0x148) / 2` | 右角色 x |

角色的立绘从底座上方 `0x86` 处开始（`0x4023B3` / `0x40254A`），所以
`figure_y = (clientH - 0xEA) / 2 + 0xEA - 0x86`。

实机客户区 604×371 时，公式给出棋盘原点 **(138, 44)**、左右角色
**40 / 506**、立绘 y **168**，与截图逐像素一致。

**结论**

| 元素 | 规则 | 依据 |
|---|---|---|
| 棋盘外框（327×328） | `x = (clientW - 328) / 2`（居中跨距 328） | 反汇编 `0x40B060` + 实机 604×371 → 138 |
| 棋盘外框 | `y = (clientH - 376) / 2 + 46` | 反汇编 `0x40B064` + 实机 604×371 → 44 |
| 网格 | 位于外框内缩 2 px | 静态分析 `SPRITE_INSET = 2` |
| 左角色 | `((clientW - 328) / 2 - 58) / 2` | 反汇编 `0x40B088` |
| 右角色 | `t + 328 + ((t - 58) / 2)` | 反汇编 `0x40B098` |
| 角色立绘 y | `(clientH - 234) / 2 + 100` | 反汇编 `0x40B08C - 0x86` |
| 最小客户区（无裁剪） | **444×372** | 由上述公式解出 |

**修正**：此前把 `0x40B078 = (clientW - 0x6C) / 2` 当成了棋盘原点，
又因为截图里棋盘看起来居中，便把实现改成「垂直居中于 HUD 之下」。
现在可以确认：`0x40B078` 是**预览球组**的 x，棋盘的原点一直是
`0x60` 的公式；截图与反汇编并不矛盾，之前只是命名错了。

> 教训：常量必须先确认语义再写进规格。`0x40B078/0x40B07C` 现确认为
> 预览球组的 X/Y，`0x40B060/0x40B064` 才是棋盘原点。

## 5e. ⭐ 统计窗口的内容已确认（菜单 513 / F5）

实机发送 `WM_COMMAND 513` 后，原作创建一个**独立的非模态窗口**
（类名 `XGrdCptDialog`，标题 `统计`，`WS_EX_TOOLWINDOW`），
客户区 **154×289**，共 **8 行 × 36 px**。证据：
`C:\bb\shots\stats_client.png`（客户区）与 `stats_window.png`（含边框）。

每行左侧是一个 36×36 的精灵槽（第 0 行是空格子，第 1–7 行是七种球），
右侧文字格式由 `0x404345` 附近的绘制循环与字符串 `0x40A4AF` / `0x40A4B9`
确定：

```text
<count> (<percent>%)              # 第 0 行：空格子数
<count> (<percent>%),消除-<N>     # 第 1..7 行：该颜色球数 + 本局累计消除数
percent = count * 100 / 81        # 整除；81 是硬编码的棋盘格数
```

| 事实 | 依据 |
|---|---|
| 8 行：空格子 + 7 种颜色 | 循环 `0x40433C` `cmp $0x8` |
| 百分比分母固定 81，向下取整 | `0x4043AD` `mov $0x51` + `idiv` |
| `消除-N` 的 N 是**本局累计**、按颜色 | `0x401C7A` `add %edx,0x40B2C4(,%eax,4)` |
| 新局把 8 个计数器清零 | `0x40282F` |
| 窗口开关由 INI `ShowStatistics` 控制，默认 0 | 实机 `WinLinez.INI` + `0x4013FF` / `0x40352C` |

**实现**：`Engine::colour_counts` / `cleared_counts` 保存同样的统计，
`app::game::stats_panel` 绘制同构面板；菜单 513 / F5 切换
`Overlay::Statistics`（重设计后为居中模态卡片，不再持久化）。

## 5f. ⭐ 消除动画的时序已确认

`C:\bb\shots\clear5\f000.png … f051.png` 是 30 ms 间隔的连拍。逐帧差分给出：

| 阶段 | 帧 | 时长 | 观察 |
|---|---|---|---|
| 移动球沿路径逐格走 | f1–f7 | 约 60 ms/格 | 同一颗球依次出现在 (6,6)→(7,6)→(8,6)→(8,5) |
| 消线溶解 | f8–f12 | 约 100 ms | 5 颗球同时变成稀疏斑点（313/536 像素），再变成 185，然后空 |
| 胜者立绘动画 | f15–f21 | 约 420 ms | 右侧挑战者上移约 5 px 后回位 |
| 静止 | f22–f51 | — | 画面不再变化 |

反汇编与之吻合：消除函数 `0x401BD4` 对标记为 `0x40` 的格子做 **两轮**绘制，
每轮结束 `Sleep(50)`（`0x401C48`）；第二轮才把格子清零并把消除数累加到
`0x40B2C4`。因此溶解是 **2 × 50 ms**，不是逐球消失。

**实现**：
- `Game::move_anim` 先按 `find_path` 的路径逐格滑动（60 ms/格，短移动最少
  180 ms），**动画结束才调用 `engine.move_ball`**；源格用空格底板盖住，移动球
  按格中心插值绘制，路径同时高亮。事件循环在动画期间切到 `Poll`，否则
  `Wait` 模式下移动只推进一帧就停住。
- `Game::clear_anim` 保存被消除的 `(cell, colour)`，`CLEAR_STEP = 50 ms`；
- `clear_animation_commands` 用 3×3 碎片近似原作斑点：第一轮保留 5/9，
  第二轮保留 3/9；
- `win_lift` 让挑战者纹章在 420 ms 内上跳一次；
- 关闭“减少动效”时跳过以上动画。

## 5g. ⭐ 默认窗口、HUD 与配色（本轮复核新增）

### 默认尺寸：外层 620×430，客户区 604×371

反汇编 `WinMain` 的窗口创建路径给出了**出厂默认值**（不是 INI 里的用户设置）：

| 代码 | 调用 | 值 |
|---|---|---|
| `0x40123c` | `GetPrivateProfileIntA(..., "WindowWidth", 0x26C, ...)` | **620** |
| `0x401257` | `GetPrivateProfileIntA(..., "WindowHeight", 0x1AE, ...)` | **430** |
| `0x4011d9` | 默认 X = `(GetSystemMetrics(SM_CXSCREEN) - 620) / 2` | 屏幕居中 |
| `0x40120b` | 默认 Y = `(GetSystemMetrics(SM_CYSCREEN) - 430) / 2` | 屏幕居中 |

`CreateWindowExA` 直接把 620×430 作为**外层窗口**尺寸，所以在
Windows 11 200% 缩放、本机窗口边框下客户区正好是 **604×371**——与
200% 截图里量到的棋盘/角色坐标完全一致。

**实现**：`Settings::default()` 存 **604×396** 逻辑客户区：
372 px 内容（棋盘最小可完整容纳的高度，棋盘原点仍为 (138, 44)）+
20 px 自绘菜单条 + **4 px 底部边框预留**（原作的下边框在客户区之外；
自绘时必须在客户区内留出空间，否则棋盘会压住边框）。
默认位置为 `-1`（屏幕居中）；窗口大小/位置在退出时写回存档，下次启动恢复。

### 配色（从 200% 实机截图逐像素采样）

| 区域 | 颜色 |
|---|---|
| 菜单 / HUD 底 | **#F0F0F0**（Windows 10/11 的 `COLOR_BTNFACE`；原作调用 `GetSysColor`） |
| 棋盘外背景 | **#000000** |
| 空格底板 | **#C0C0C0** |
| 格子立体边 | 上/左 **#FFFFFF**，下/右 **#292929**，最外 1 px 黑缝 |

### HiDPI 输入

窗口事件给的是**物理像素**，而布局是**逻辑单位**。此前把物理坐标直接
送进 `hit_cell`，在 200% 屏上点击位置整体偏移一倍，表现为“点了没反应、
不能移动小球”。现在统一经 `Viewport` 反算：

```
logical = (physical - content_rect.origin) / content_scale
```

该换算同时覆盖 letterbox（固定分辨率模式）与多屏不同 DPI。已在
200% 实机上用合成鼠标事件验证：选中 → 相邻空格 → `Moved`，源格清空、
目标格出现同色球。
