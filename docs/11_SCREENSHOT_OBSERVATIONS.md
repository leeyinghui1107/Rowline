# 11 · 原版实机截图观察（黑盒证据）

> 证据来源：原版 WinLinez v1.30 在 Windows 上的实机运行截图（用户提供）。
> 本文件记录**从截图直接读到的事实**，并标注它证实/修正了哪些静态分析结论。
> 与 `docs/03_FEATURE_SPEC.md` 的关系：截图是**行为层面**的最高优先级证据，
> 静态分析结论与之冲突时以截图为准。

---

## 1. 窗口结构

| 观察 | 结论 | 与静态分析的关系 |
|---|---|---|
| 标题栏 `WinLinez v1.30`，图标为蓝色圆点 | 版本号与 `VERSION/1` 资源一致 | ✅ 证实 |
| 标题栏下是**独立的菜单栏**：`文件(F)` / `选项(O)` | **只有两个顶层菜单** | ✅ 证实 `RT_MENU` 解析（`文件` / `选项`） |
| 菜单栏下是**独立的 HUD 栏** | HUD 不在棋盘区内部，而是横跨整个客户区 | ⚠️ 修正了"侧栏"的猜测 |
| 最右侧有一个下拉菜单正在展开（截图 1 右上角） | 菜单是弹出式下拉 | ✅ 与 Win32 菜单行为一致 |

**修正**：我此前把 HUD 画成棋盘右侧的**竖向侧栏**。原版是**顶部横栏**。见 §3。

## 2. HUD 栏布局（自左向右）

```
┌──────────┐   ┌────┐  ┌───┬───┬───┐   ┌────┐   ┌──────────┐
│  100     │   │下组 │  │ ● │ ● │ ● │   │颜色│   │   160    │
└──────────┘   └────┘  └───┴───┴───┘   └────┘   └──────────┘
   分数框        标签     预览球组      标签        分数框
```

| 元素 | 观察 | 含义 |
|---|---|---|
| 左分数框 | `100` | 某个分数（**当前分或最高分，待定**） |
| `下组` | 标签 | **"下一组"** |
| 三个预览格 | 截图 1：红/品红/黄；截图 2：黄/红/暗红 | **下一组 = 3 颗球** ⭐ |
| `颜色` | 标签 | **"颜色/形状"** 模式指示（对应菜单项 `使用形状`） |
| 右分数框 | `160` | 另一个分数 |

### 2.1 ⭐ 最重要的新事实：**下一组是 3 颗球**

这直接修正了 `docs/03` §8 里"补球数量 ⬜ 未定"的假设：

* 游戏**预先预告接下来的 3 颗球**；
* 因此"补球"的自然实现是：维护一个长度为 3 的**待用球队列**，队首的球被消耗时从队尾补入新的随机球；
* 这解释了**截图中稀疏的棋盘**——棋盘并非初始满盘。
  （新局的球数后来由截图 1 直接确定为 **5 颗**，见 §5c。）

> 静态分析只能看到 `GetPrivateProfileIntA` 读 `ShowNext`（"显示下一组"），
> **看不到"下一组 = 3 颗"**。这是截图独有的信息。

### 2.2 两个分数框

截图 1（游戏结束）与截图 2 都显示 `100` / `160`。静态分析确认存在两个独立的量：

| 量 | 地址 | 含义 |
|---|---|---|
| 当前局分数 | `0x40B06C` | 本局得分 |
| 最高分 | `0x40B2A8` | 榜单第 1 条的分数（默认 100） |

**假设**：左框 = 当前分（100），右框 = 最高分（160）？还是相反？
静态分析里 `0x40B2A8`（最高分）的**默认值正是 100**（ wiped 榜单的记录 0 = 100 分），
因此 **右框 `160` 更可能是当前分，左框 `100` 是最高分**（即默认榜单的 100）。
⚠️ 仍需 `BB-N02`（HUD 数值表）以 100% 确认。

## 3. 棋盘区

| 观察 | 结论 |
|---|---|
| 网格 **9 列 × 9 行** | ✅ 证实静态分析（`cmp esi, 9` / `cmp ebx, 9`） |
| 每个格子是**浅灰底 (#C0C0C0) + 深色边框** | 格子有独立的边框，比纯色块更立体 |
| 格子外的左右区域是**纯黑** | 棋盘区的**背景是黑色**，不是灰色 |
| 格子是圆角矩形 | 与其它控件的圆角一致 |
| 有球时球**居中**在格内 | 与 `srcX = value*36 + set*288` 的取样一致 |

**修正**：我此前把棋盘背景实现为浅灰。原版是**黑底 + 浅灰格子**。

## 4. 左右装饰（"国王" 与 "挑战者"）

| 观察 | 结论 |
|---|---|
| 左侧一个**红色国王**（戴王冠、持权杖），下方标注 `国王` | **CPU 一方**（HUD 左框是它的分数） |
| 右侧一个**品红国王**（持剑），下方标注 `挑战者` | **玩家一方**（HUD 右框是它的分数） |
| 两个角色都站在**金属圆柱底座**上 | 底座是精灵集中的**竖直渐变金属条** |

这两个角色来自**精灵集顶部的角色区**（`assets/png/atlas_chars.png`），
其中：
* 第一行是**红色国王的 7 帧动画**；
* 第二行是**品红国王的 7 帧动画**；
* 右侧的**竖直金属条**是两个角色共用的底座。

> 静态分析只把这一区域当作"未使用的高分辨率素材"，
> 截图证明它是**棋盘两侧的常驻装饰**。

⚠️ 角色在精灵集中**不落在 36 px 栅格上**（国王约 45×95 px），
因此需要独立的取样矩形定义 —— 见 §6。

> **合规决定**：这些角色像素是原作的受版权保护美术（REPORT.md R2），
> **不得**进入重构版。实现改为**自制纹章**：左红冕章（王冠）/ 右品红剑章（剑），
> 同样立在金属底座上、同样带 `国王` / `挑战者` 标注。
> 行为一致（位置、标注、两侧分列），美术是新的。

## 5. 游戏结束对话框

| 观察 | 结论 |
|---|---|
| 标题 `WinLinez v1.30` | 与 `VERSION/1` 一致 |
| 一个**黄色警告三角**图标 | `MB_ICONWARNING` |
| 文字 `游戏结束!` | 简体中文 |
| 一个 `确定` 按钮 | **只有 OK**，不是 Yes/No |

> 静态分析找到的 `MessageBoxA` 标志 `0x34` = `MB_YESNO|MB_ICONWARNING`，
> 那是**反作弊**提示（带是/否）。
> **本对话框是另一处** `MessageBoxA`，标志应为 `MB_ICONWARNING`（仅 OK）。
> 这解释了为什么会出现"两个不同标志的 MessageBoxA"。

## 5b. ⭐ 决定性证据：这是**人机对战**，且榜单格式已确定

第三张截图（总榜对话框）给出了此前完全未知的事实：

```
总榜
┌────────────────────────────────┐
│  1. 挑战者                 160 │
│  2. 国王                   100 │
│  3. - 空的 -                 0 │
│  4. - 空的 -                 0 │
│  ...                           │
│  16. - 空的 -                0 │
└────────────────────────────────┘
   [清除]              [确定(O)]
```

| 事实 | 含义 |
|---|---|
| 榜单**恰好 16 行** | 与静态分析的 `TABLE_LEN = 16 × 32 B` 完全吻合 ⭐ |
| 空槽的占位文字是 **`- 空的 -`**，分数 `0` | 榜单的渲染格式已确定 |
| 行的格式是 **`N. 名字    分数`** | 同上 |
| 第 1 名 `挑战者` 160 分，第 2 名 `国王` 100 分 | **游戏是人机对战**：CPU 叫「国王」，玩家默认叫「挑战者」 |
| 对话框有两个按钮：**清除**（带禁止图标）与 **确定(O)**（带勾图标） | 榜单可清空 |

**HUD 两个分数框的归属（终于可以定案）**

| 截图 | 左框 | 右框 | 解读 |
|---|---|---|---|
| 第 1 张（**新局**，玩家刚开局） | **160** | **0** | 国王=160（历史最佳），挑战者=0（当前局） |
| 第 2/3 张 | **100** | **160** | 国王=100，挑战者=160 |
| 榜单 | — | 挑战者 160 / 国王 100 | 与 HUD 完全一致 ✅ |

→ **左框 = 国王（CPU）的分数，右框 = 挑战者（玩家）的分数。**
左框同时也是「最高分」——新局时它显示上一局的 160，玩家从 0 开始。

**名称输入对话框**（第 2 张截图）

| 元素 | 内容 |
|---|---|
| 提示 | `输入你的名字:` |
| 输入框 | 预填 **`挑战者`** |
| 按钮 | `确定(O)`（带勾图标） |

→ 玩家的默认名就是 `挑战者`；破纪录时会弹这个框。

## 5c. 新局的棋盘是**稀疏**的：恰好 5 颗随机球

第 1 张截图是**初始化界面**（新局），棋盘 9×9 里**只有 5 颗球**，散落分布：

| 位置 | 颜色 |
|---|---|
| 行 2 / 列 1 | 青 |
| 行 3 / 列 4 | 黄 |
| 行 7 / 列 5 | 品红 |
| 行 7 / 列 7 | 黄 |
| 行 8 / 列 5 | 蓝 |

→ 这**否证**了我此前 `RuleModel::initial_fill = 80%`（初始填满）的猜测。
**新局 = 在空棋盘上随机放 5 颗球**，然后预告「下一组」的 3 颗。

**实现已按此更正**：`RuleModel::initial_balls = 5`，
Python / C / Rust 三份实现的 RNG 消耗顺序完全一致（先取位置、再取颜色），
四方差分门重新冻结基线后全绿。

## 5d. ⭐ 布局：棋盘**居中**，两个角色**分列两侧**

第 1 张是**窗口模式（桌面 200% 缩放）**，第 2 张是**同一局的��屏**。
两张图状态完全相同（5 颗球位置、3 颗预览球、160/0 分数都一致），
因此可以**交叉验证布局**。

用**比例**（与缩放无关）测量全屏图：

| 量 | 比例 | 换算成逻辑像素（格 = 36） |
|---|---|---|
| 棋盘网格中心 / 窗口宽 | **0.500** | 棋盘**精确居中** |
| 右侧角色底座 / 窗口宽 | 0.795 | 与二进制公式 `(right-0x148)/2 + 0x148 + ((right-0x148)/2-0x3A)/2` 吻合（误差 1.3%） |
| 左侧角色底座 / 窗口宽 | 0.207 | 与右侧**对称** |

**结论**

| 元素 | 规则 | 依据 |
|---|---|---|
| 棋盘外框（327×328） | **水平居中**：`frame_x = (clientW - 327) / 2` | 截图（全屏中心误差 0） |
| 棋盘外框 | **垂直居中于 HUD 之下**：`y = (HUD 底 + 客户区高) / 2` | 截图（两种窗口模式一致） |
| 网格 | 位于外框内缩 2 px | 静态分析 `SPRITE_INSET = 2` |
| 左角色 | `clientW - right_figure_x - 58` | 对称 |
| 右角色 | 二进制原公式 | 截图吻合 1.3% |

**⚠️ 与我此前规格的冲突**：我原先把 `[0x40B078] = (right - 0x6C) / 2` 当成棋盘原点的 X。
重新反汇编 `0x402EA7` 确认该常量确实是 `0x6C = 108`，
但**截图显示棋盘是居中的**，两者矛盾。
按「直接行为证据优先于实现细节」的原则，**实现改为居中**，
并把该常量的确切用途（尚未识别）标注为待查。

> 教训：这一处我最初是**凭猜测给常量命名**（"boardOriginX"），
> 结果把一个不相关的量当成了布局公式。**常量必须先确认语义再写进规格。**
